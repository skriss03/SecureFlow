SecureFlow Developer Kick-off Guide

Scan your own application from your machine and get a resilience, threat-model and vulnerability (CVE) report at a link you can open and share. Same one command for every tech stack.

How it works

You run one command inside your project folder. SecureFlow reads the project on your machine, sends only what it needs to a SecureFlow server, and prints a link to the report. The command shows each step as it goes.

1 · Read locallyIt picks deployment files, configuration, service-wiring code and dependency versions. Nothing is compiled or run.Secret values are replaced with ***REDACTED*** before anything leaves your machine.
2 · UploadThe selected files and the dependency list go to the SecureFlow server.Add --dry-run to see exactly what would be sent, without sending it.
3 · AnalyseThe server rebuilds your architecture with AI, applies resilience and security rules, and checks every dependency against known CVEs.You get a report link, scores and a pass/fail exit code.
Same link every time. Scanning the same repository and branch again updates the same report, so the link you shared stays valid, and the report keeps the score history.

Before you start

You needWhy
The SecureFlow repository on your machineIt contains the server and the install scripts used below.
.NET 10 SDK, Node.js (LTS) and GitOnly to run the local SecureFlow server. The secureflow command itself needs none of them.
An AI key for the serverThe server uses an AI model to rebuild your architecture. See step 1. Without one you still get a CVE-only report.
Your project in a Git folderThe report is named after the repository and branch. Any folder works, but a Git repo gives the best names.

The commands below are for Windows PowerShell. On macOS or Linux the same secureflow commands work unchanged; only the install and server-start commands differ, and those are noted where needed.

1. Start the SecureFlow server

For the local test, the server runs on your own machine. (Later it moves to the shared OpenShift server and only a URL changes. See Moving to the shared server.)

  1. Save your AI key Keys are stored as user secrets, outside the repository, so they can never be committed. Pick the line that matches where your key came from. 
    # Key from console.anthropic.com (starts with sk-ant-)
dotnet user-secrets set "Ai:AnthropicApiKey" "<your-key>" --project src/SecureFlow.Api

# Key from Microsoft Foundry: also save the provider, resource and deployment names
dotnet user-secrets set "Ai:AnthropicApiKey"        "<your-foundry-key>"       --project src/SecureFlow.Api
dotnet user-secrets set "Ai:Provider"               "foundry"                   --project src/SecureFlow.Api
dotnet user-secrets set "Ai:FoundryResourceName"    "<resource-name>"          --project src/SecureFlow.Api
dotnet user-secrets set "Ai:FoundryDeploymentName"  "<deployment-name>"        --project src/SecureFlow.Api
    In Foundry, open Build → Models → your deployment. The API key is in the right-hand panel. The resource name is the first part of the endpoint https://<resource-name>.services.ai.azure.com, and the deployment name is the name in the list (for example claude-opus-5).
    Never paste the key into a chat, an email or a file in the repository. Paste it only into the command above.
  2. Start the server From the SecureFlow repository folder: 
    .\scripts\run.ps1
    Leave this window open while you use SecureFlow. It serves everything at http://localhost:5180.
  3. Check that it is healthy In a second terminal: 
    curl http://localhost:5180/api/health
    Look for "status":"ok" and "available":true under ai. The server also prints a warning at startup if your AI key looks like it is for the wrong provider.
No AI key yet? The scan still works and gives you the dependency CVE report. The report then says "Architecture not analysed" instead of showing resilience and security scores.

2. Install the secureflow command (once per machine)

This puts one self-contained program on your PATH. It needs no .NET, Java, Node or Python. After this you use the same command in every project.

  1. Build the client files (local test only; in your organisation these will already be in Artifactory) 
    .\scripts\publish-clients.ps1
  2. Install 
    .\scripts\install-cli.ps1

    Once the files are in Artifactory, developers will install from there instead:

    .\scripts\install-cli.ps1 -BaseUrl https://artifactory.example.com/artifactory/generic-local/secureflow

    macOS / Linux:

    SECUREFLOW_CLI_BASE_URL=https://artifactory.example.com/artifactory/generic-local/secureflow sh scripts/install-cli.sh
  3. Open a new terminal and check it 
    secureflow --version
    You should see secureflow 0.1.0 and the folder it was installed in (~\.secureflow\bin). A new terminal is needed because an already-open one does not see the updated PATH.
    If it shows a different folder, an older secureflow is earlier on your PATH. The installer warns you about this. Remove the older one (for example dotnet tool uninstall -g secureflow.cli).

3. Run your first scan

This is the same for every tech stack. Go to your project folder and run the scan.

  1. Go to your project 
    cd C:\path\to\your\project
  2. Preview what would be sent (optional, sends nothing) 
    secureflow scan --dry-run
    You see the file list, how many dependencies were found, and how many secret values were redacted.
  3. Scan 
    secureflow scan --open
    The command prints three labelled steps and then the result. --open opens the report in your browser when it is ready. The AI step usually takes one to a few minutes. 
    [1/3] Reading the project on this machine ...
[2/3] Uploading 39 files and 15 dependency versions to http://localhost:5180 as 'libfintx@main'
[3/3] Server is analysing: architecture model (AI), resilience + STRIDE rules, CVE check

libfintx  (scan #1, main @ 46316f1)
  Resilience 45 (D)   Security 23 (F)
  Open findings: 64  (4 Critical, 25 High, 27 Medium, 8 Low)   of which CVEs: 14
  Report: http://localhost:5180/p/79d9dfe2ca

4. Read the report

Open the Report: link. It has these parts:

PartWhat it tells you
ScoresResilience and Security, 0 to 100 with a letter grade. An open Critical finding caps a score at 49, an open High at 74.
FindingsEach one names the affected components, the rule, the evidence (file and line), why it matters, and how to fix it. Filter by severity or type: resilience, security, or vulnerability (CVE).
ModelThe architecture SecureFlow rebuilt from your code: services, databases, queues, and the calls between them. Click a component and choose Simulate failure to see what else goes down with it.
FixesAsk for an AI-proposed fix on a finding, apply it, and watch the score update.
Report tabExecutive summary and top risks. Print it or save it as PDF to share.
CVE findingsReal published advisories for a dependency version in your project, with the version to upgrade to. They come from the OSV database, not from the AI.
The CVE check only uses versions that are written down in your project (manifest or lockfile). Versions that a parent or BOM decides, such as Spring Boot starters with no <version>, cannot be known without resolving it, so SecureFlow skips them rather than guessing.

Java / Spring Boot with Maven Full support
Run
cd your-service then secureflow scan --open
Architecture signals
pom.xml, application*.yml / .properties, bootstrap.yml, Dockerfile, Kubernetes / OpenShift / Helm files, CI pipelines. In code: RestTemplate, WebClient, Feign clients, Kafka and Rabbit listeners, JdbcTemplate, Resilience4j, Spring Security.

Any other stack (Ruby, PHP, Rust, ...) Architecture only

SecureFlow still reads the files that describe how the system is deployed: Dockerfile, docker-compose, Kubernetes / OpenShift / Helm, Terraform, Bicep, CI pipelines, configuration and the README. You get an architecture model, rules and scores. There is no CVE check for stacks without a supported manifest.

cd C:\path\to\your-project
secureflow scan --open

If your service wiring lives in files SecureFlow does not pick up, add patterns in a .secureflow.yml file at the repo root, with no code change:

ingest:
  extraPriorityPatterns:
    - 'config/.*\.rb$'
  extraWiringSignals:
    - GrpcChannel
    - Faraday

No code needed: upload the architecture diagram you already have. In the web UI use Diagram from any tool, or from a terminal:

secureflow diagram architecture.mmd --dry-run      # parse + rules on this machine, nothing sent

"Parsed exactly" means no AI and the same result every time: the same system drawn in Visio, Mermaid or draw.io gives the same findings. Put replica counts, protocols and auth in your labels (x2, HTTPS, JWT, no auth) and draw zones as boxes around services for the most precise report. Dashed arrows are read as asynchronous.

Useful options

These work the same on every stack.

OptionWhat it does
--dry-runShow what would be sent. Nothing is uploaded.
--openOpen the report in your browser when it is ready.
--fail-on highExit with code 2 if an open finding is High or Critical. Values: low, medium, high, critical.
--group "Payments Team"Put the project on that team's dashboard.
--name "Orders Service"Set the display name. Default is the repository name.
--path services\ordersScan a sub-folder, for example one module of a monorepo.
--out report.mdAlso save the report as a Markdown file.
--no-waitUpload and print the link without waiting for the analysis.
--server URL / --token TChoose the server and give your token. Normally set once in your environment instead (below).
secureflow configShow the settings in effect and where each one came from.
secureflow --helpList every command and option.

Where settings come from

Each setting is looked up in this order, and the first one found wins:

  1. The command-line option, for example --fail-on high
  2. An environment variable, for example SECUREFLOW_FAIL_ON=high
  3. .secureflow.yml in your repository
  4. ~\.secureflow\config.yml in your user folder
  5. The built-in default

Example .secureflow.yml in a repository. Keep the server address and token out of the repository:

name: orders-service
group: Payments Team
failOn: high

Example ~\.secureflow\config.yml, your personal settings:

server: http://localhost:5180
# token: <your team token>      (needed only when the server requires one)

Fail a build on serious findings

Add --fail-on to turn the scan into a quality gate. The command exits with a code your build or pipeline understands:

Exit codeMeaning
0Finished, and nothing at or above your threshold is open.
2Finished, but open findings reach your threshold. The build should fail.
1The scan could not run (server unreachable, bad token, and so on).
secureflow scan --fail-on critical
echo $LASTEXITCODE        # 2 means the gate failed

In a pipeline, run the same command. A ready-made GitHub Actions example is in samples/ci/secureflow-gate.yml. For Maven, bind the plugin to the verify phase in a profile and run mvn verify -Psecureflow.

If you decide a finding is acceptable, mark it Accepted in the report. It stays accepted on later scans, and no longer counts toward the gate.

Troubleshooting

You seeWhat it means and what to do
secureflow is not recognisedOpen a new terminal after installing. If it still fails, run .\scripts\install-cli.ps1 again.
secureflow --version shows a different folderAn older copy is earlier on your PATH. Remove it, for example dotnet tool uninstall -g secureflow.cli.
cannot reach SecureFlow at http://localhost:5180The server is not running. Start it with .\scripts\run.ps1, or check the address in secureflow config.
server returned 401 UnauthorizedThe server requires a token. Set SECUREFLOW_TOKEN or use --token. Ask the SecureFlow owner for one.
invalid x-api-key (in the report log)The AI key on the server is wrong. A key that does not start with sk-ant- is not an Anthropic key. If it came from Microsoft Foundry, set Ai:Provider=foundry with the resource and deployment names (step 1). Then restart the server.
AI provider unavailable / "Architecture not analysed"The server has no working AI key. You still get the CVE report. Add a key (step 1) and scan again for the full report.
No CVEs found, but you expected someVersions must be written in a manifest or lockfile. Ranges (^1.2, >=2.0) and versions set by a parent or BOM are skipped. Pin the version or commit the lockfile. Also check the dry run says "Resolved N pinned dependencies".
The report misses a service or callThe file that shows it was not picked up. Run --dry-run to see the list, then add its path or a code pattern in .secureflow.yml (ingest.extraPriorityPatterns or extraWiringSignals).
A secret value appears in the reportRedaction replaces values for keys such as password, secret, token, apikey and connection string. If yours has a different name, add it with redaction.keyPattern in .secureflow.yml, and check with --dry-run before uploading.
A scan of this project is already runningAnother scan of the same repository and branch is still in progress. The command follows it; wait for it to finish.
Not sure what is being used? Run secureflow config. It lists every setting, its value (the token is masked), and whether it came from a flag, an environment variable, your repository file, your user file or a default.

Moving to the shared (OpenShift) server

Nothing in your project changes. You only tell the command where the shared server is and give it your token:

# one time, in PowerShell
[Environment]::SetEnvironmentVariable("SECUREFLOW_SERVER", "https://secureflow.apps.<cluster>", "User")
[Environment]::SetEnvironmentVariable("SECUREFLOW_TOKEN",  "<your team token>",               "User")

Or put the same two lines in ~\.secureflow\config.yml:

server: https://secureflow.apps.<cluster>
token: <your team token>

Then run secureflow scan exactly as before. The report link now points at the shared server, is kept for the retention period (30 days by default), and appears on your team's dashboard if you set a group.

For the SecureFlow owner: the server image, the OpenShift files and the full list of server settings are in docs/developer-integration.md and deploy/openshift/.
