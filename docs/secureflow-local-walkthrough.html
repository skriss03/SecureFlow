Demoing after this VM is gone

Three constraints, stated plainly:

ConstraintWhat it rules out
This VDI will be wipedAnything that only exists on local disk here — screenshots and video are already solved by committing them (above).
The AI key only exists on this VMRunning a new scan, with a new input, anywhere else — the AI call would fail with no key.
Only git push is allowed out of this machineNo uploading to cloud storage, no deploying a server elsewhere, no emailing files.

The video solves "show it once, anywhere, to anyone" — it needs nothing but a browser. But if you want to show the running app again — click around live, open a different finding, show the blast radius on a different node — you need the server actually running, and that means the AI calls it already made need to work without the key. That turns out to be possible, and I tested it for real before writing this.

Verified on this machine, just now: I started a second copy of the server with the real key replaced by the placeholder string "placeholder-no-real-key-needed", offline mode forced on, and a cache folder containing only 7 small JSON files (no screenshots, no code, just recorded AI responses). I then ran secureflow diagram northbank.vsdx fresh against it. Model, AI review and the fix proposal all replayed correctly — same scores, same fix text, same everything — and the project's own log recorded it honestly: Replayed analyze from cache (749cf0d0)… and Replayed fix from cache (0b08016d)…. No network call was made, and none could have succeeded with that key even if attempted.

The offline-replay recipe

On any machine with just the .NET 10 runtime (no API key, no network needed) — a judge's laptop, a conference room PC, anything:

  1. Clone the repo (public GitHub access is all this needs): 
    git clone https://github.com/skriss03/SecureFlow.git
cd SecureFlow
git checkout feature/tool-agnostic-diagram-import   # or wherever this lands after review
  2. Point the server at the seed cache and force offline mode. The values below must match exactly what the cache was recorded under — see "Why this works". 
    # PowerShell
$env:SECUREFLOW_AI_OFFLINE = '1'
$env:Ai__CacheDir = (Resolve-Path samples\demo-replay-cache)
$env:Ai__Provider = 'foundry'
$env:Ai__FoundryDeploymentName = 'claude-opus-5'
$env:Ai__FoundryResourceName = 'placeholder'
$env:Ai__AnthropicApiKey = 'placeholder'
  3. Run it: 
    dotnet run --project src/SecureFlow.Api
    Health check should show "offline":true,"ai":{"available":true} — available with a placeholder key, because nothing is actually calling out.
  4. Scan the same file again and it replays instead of failing: 
    dotnet run --project src/SecureFlow.Cli -- diagram samples/diagrams/northbank.vsdx --open
    You get the identical report this walkthrough shows: Resilience 36 (F), Security 74 (C), the same 42 findings, and the same AI-proposed fix for Payments DB — all without a real key anywhere on the machine.
This exact recipe only reproduces this one scenario (the NorthBank .vsdx upload, its AI review, and the fix for the Payments DB single point of failure). Click into a different finding's fix, or upload a different file, and you'll get a clean, honest Offline mode: no cached response — run once online to record it error rather than a silent failure or a fake answer. See "Adding more scenarios" to extend what's covered before access is lost.

Why this works

Every AI call in SecureFlow goes through a content-addressed replay cache (src/SecureFlow.Ai/Caching/ReplayCache.cs) — it already exists for a different reason (surviving a flaky network during a live demo), and it happens to solve this problem too:

  • The cache key is a hash of the operation, the exact provider name string (e.g. claude-opus-5 (Microsoft Foundry)), and the real request content (the model, the digest, the finding). It is not a hash of the API key — the key never enters the key material at all.
  • With SECUREFLOW_AI_OFFLINE=1, a cache hit returns the recorded response; a cache miss throws a clear error instead of ever attempting the network — so there is no way for it to accidentally "half work" with a bad key.
  • The provider classes only check that a key string is non-empty at startup (so the app can start at all); they never validate it until a real network call is attempted — which offline mode guarantees never happens for a cached scenario.
  • Because the provider name is part of the key, the offline machine's Ai:Provider, model and deployment-name settings must match what was recorded exactly — that's why the recipe above pins them.

I checked every file in samples/demo-replay-cache/ for anything secret-shaped (API key patterns, bearer tokens) before committing them — they contain only the operation name, the provider name, a timestamp, and the AI's own response text.

Adding more scenarios — do this before access is lost

The cache only grows while a real key still works, which is only on this VM, only until it's wiped. For every additional thing you might want to click on in a future offline demo (a different sample's AI review, a different fix, a repo scan's AI extraction), do this now:

  1. Run it for real, once, on this VM, with the real key (exactly as today).
  2. Find the new file(s) it created in src/SecureFlow.Api/data/cache/ (sorted by time, or grep -l for distinctive text as I did above).
  3. Copy them into samples/demo-replay-cache/ and commit.

Each file is a few KB of text — there's no practical reason not to be generous here before this environment disappears.

What this doesn't solve

  • A brand-new scan of a file nobody has fed it before still needs a real AI key. Offline replay is a rehearsed demo, not a general substitute for having a key.
  • Deterministic-only work has no such limit. Every structured diagram format (draw.io, Mermaid, PlantUML, Structurizr, Visio, Excalidraw, Gliffy), the 26 resilience/STRIDE rules, scoring and blast-radius simulation need no AI at all, on any machine, forever — only the AI review and the AI-proposed fixes are cache-dependent.
  • CVE scanning (OSV.dev) is a real network call with no replay cache today, and would need actual internet access (not an API key) to run fresh on another machine.
